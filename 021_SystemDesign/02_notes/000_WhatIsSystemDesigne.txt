0.1 WHAT IS A SYSTEM?
================================================================

DEFINITION
----------

A system is a collection of interconnected components that work
together to achieve a common goal.

A software system consists of components such as:

1. Users
2. Client applications
3. Servers
4. APIs
5. Databases
6. Caches
7. Message queues
8. External services
9. Monitoring systems

These components communicate with each other to provide a service.


EXAMPLE 1: ONLINE SHOPPING SYSTEM
---------------------------------

Suppose you want to purchase a mobile phone using an application.

The process might be:

Step 1: Open the shopping application.
Step 2: Search for a mobile phone.
Step 3: View the product details.
Step 4: Add the product to the cart.
Step 5: Place an order.
Step 6: Make payment.
Step 7: Receive order confirmation.
Step 8: Track the delivery.

Many components work together to complete this process.

ARCHITECTURE:

    +----------------------+
    |        USER          |
    +----------+-----------+
               |
               v
    +----------------------+
    |   Mobile/Web App     |
    +----------+-----------+
               |
               v
    +----------------------+
    |     Backend API      |
    +----------+-----------+
               |
       +-------+--------+
       |       |        |
       v       v        v
    Product  Order    Payment
    Service  Service  Service
       |       |        |
       v       v        v
    Product  Order    Payment
    Database Database Gateway

               |
               v
    +----------------------+
    | Notification Service |
    +----------------------+

This collection of components forms a software system.


EXAMPLE 2: WHATSAPP
------------------

A simplified messaging system may contain:

1. Mobile application
2. Authentication service
3. Message service
4. Message storage
5. Real-time communication infrastructure
6. Notification service
7. Media storage
8. Monitoring infrastructure

When a user sends a message, these components cooperate to
deliver and store the message.

IMPORTANT:

A real production system may use many additional components.
The architecture above is conceptual, not a representation of
WhatsApp's complete internal implementation.


KEY IDEA
--------

A system is not merely a program.

A program might calculate the sum of two numbers.

A software system may coordinate thousands of services, databases,
users, and network connections to accomplish a larger objective.


INTERVIEW QUESTION
------------------

Q: What is a software system?

Answer:

A software system is a collection of software components,
data stores, communication interfaces, and supporting
infrastructure that work together to provide a defined service.

0.2 WHAT IS SOFTWARE ARCHITECTURE?
================================================================

DEFINITION
----------

Software architecture describes the major components of a software
system, their responsibilities, their relationships, and the
important decisions governing how they interact.

Architecture answers questions such as:

1. What major components do we need?
2. What responsibilities does each component have?
3. How do components communicate?
4. Where is data stored?
5. How will the system scale?
6. How will failures be handled?
7. How will the system be secured?
8. How will the system be deployed?


EXAMPLE: VIDEO STREAMING APPLICATION
------------------------------------

Suppose we are designing a YouTube-like application.

Possible architectural components:

    +---------------------+
    |       Client        |
    +----------+----------+
               |
               v
    +---------------------+
    |   API Gateway       |
    +----------+----------+
               |
       +-------+--------+
       |       |        |
       v       v        v
    Video   User     Search
    Service Service  Service
       |
       v
    Video Metadata DB

    Video Upload
        |
        v
    Object Storage
        |
        v
    Transcoding Workers
        |
        v
    CDN
        |
        v
    Video Playback


The architecture determines how these components are organized
and how they cooperate.

For example:

- The video service manages video-related operations.
- Object storage holds video files.
- Transcoding workers create playback-friendly video formats.
- The CDN distributes video content closer to viewers.
- The metadata database stores information about videos.


ARCHITECTURAL DECISIONS
-----------------------

Decision 1:
Should the application be a monolith or microservices?

Decision 2:
Should we use PostgreSQL, MongoDB, or another database?

Decision 3:
Should video files be stored in a database or object storage?

Decision 4:
Should video processing happen synchronously or asynchronously?

Decision 5:
Should we use a CDN?

Each decision affects cost, complexity, performance, reliability,
and maintainability.


IMPORTANT DISTINCTION
---------------------

Architecture focuses on the overall structure and important
system-wide decisions.

Detailed class structures, method signatures, and algorithms
are usually part of lower-level design.

However, architecture and detailed design influence each other.


INTERVIEW QUESTION
------------------

Q: What is software architecture?

Answer:

Software architecture defines the major components of a system,
their responsibilities, interactions, and significant technical
decisions that determine how the system behaves and evolves.

0.3 WHAT IS SYSTEM DESIGN?
================================================================

DEFINITION
----------

System Design is the process of determining how a software system
will satisfy its requirements through appropriate components,
data models, interfaces, algorithms, infrastructure, and
architectural decisions.

It involves deciding:

1. What the system must do.
2. Who will use it.
3. How components will communicate.
4. How data will be stored.
5. How much traffic it must support.
6. How it will handle failures.
7. How it will remain secure.
8. How it will evolve as requirements change.


EXAMPLE: DESIGNING A URL SHORTENER
----------------------------------

A URL shortener converts a long URL into a short URL.

Example:

Original URL:
https://example.com/products/electronics/mobile/12345

Short URL:
https://short.example/aB91x

When someone opens the short URL, the system redirects them
to the original URL.


STEP 1: REQUIREMENTS
--------------------

Functional requirements:

- Create a short URL.
- Redirect users to the original URL.
- Optionally support expiration.
- Optionally collect click analytics.

Non-functional requirements:

- Low redirection latency.
- High availability.
- Durable URL mappings.
- Protection against abuse.
- Support for growing traffic.


STEP 2: IDENTIFY COMPONENTS
---------------------------

1. Client
2. API server
3. URL generation component
4. Database
5. Cache
6. Load balancer
7. Monitoring system


STEP 3: DESIGN THE ARCHITECTURE
-------------------------------

             +----------------+
             |     Client     |
             +--------+-------+
                      |
                      v
             +----------------+
             | Load Balancer  |
             +--------+-------+
                      |
                      v
             +----------------+
             |   API Server   |
             +--------+-------+
                      |
              +-------+-------+
              |               |
              v               v
          +-------+       +--------+
          | Cache |       |Database|
          +-------+       +--------+


STEP 4: DEFINE THE DATA MODEL
-----------------------------

A URL mapping could contain:

URLMapping:
    id
    short_code
    original_url
    created_at
    expires_at


STEP 5: DEFINE THE REDIRECTION FLOW
-----------------------------------

1. User opens a short URL.
2. The request reaches the load balancer.
3. The load balancer selects an API server.
4. The server checks the cache.
5. If the mapping is cached, retrieve the original URL.
6. Otherwise, query the database.
7. Optionally populate the cache.
8. Return an HTTP redirect response.

For example:

GET /aB91x

Response:

HTTP/1.1 302 Found
Location: https://example.com/products/electronics/mobile/12345


STEP 6: CONSIDER SCALE
----------------------

What happens if 100 users use the system?

A simple application server and database may be sufficient.

What happens if 1 million users use it daily?

We may need:

- Multiple API servers.
- Load balancing.
- Database indexes.
- Caching.
- Rate limiting.
- Monitoring.

What happens if traffic grows much further?

We may investigate database replication, partitioning, or sharding,
depending on the workload and actual bottlenecks.


IMPORTANT
---------

System design is not about adding every possible technology.

It is about selecting the simplest architecture that satisfies
the actual requirements while leaving a reasonable path for growth.


================================================================
0.4 WHY IS SYSTEM DESIGN REQUIRED?
================================================================

Consider an application that works perfectly for 100 users.

After becoming popular, it receives requests from 1 million users.

The application begins experiencing:

- Slow responses
- Database overload
- Memory exhaustion
- Failed requests
- Duplicate operations
- Service outages
- Unexpected infrastructure costs


WHY DOES THIS HAPPEN?
---------------------

Because a system designed for a small workload may not be suitable
for a large workload.

System design helps engineers anticipate and address these issues.


REASON 1: SCALABILITY
---------------------

Can the system handle increasing users and requests?

REASON 2: PERFORMANCE
---------------------

Can the system respond quickly enough?

REASON 3: RELIABILITY
---------------------

Can the system continue functioning correctly despite failures?

REASON 4: AVAILABILITY
----------------------

Can users access the service when they need it?

REASON 5: SECURITY
------------------

Can the system protect user data and prevent unauthorized access?

REASON 6: COST
--------------

Can the system satisfy requirements without wasting resources?

REASON 7: MAINTAINABILITY
-------------------------

Can developers safely modify the system as requirements evolve?

REASON 8: DATA CORRECTNESS
--------------------------

Can the system prevent invalid states, lost updates, and
incorrect transactions?


REAL-WORLD EXAMPLE: TICKET BOOKING
----------------------------------

Suppose only one seat remains for a concert.

Two users attempt to purchase that seat simultaneously.

Without appropriate concurrency control:

User A reads: Seat available.
User B reads: Seat available.

User A books the seat.
User B also books the seat.

Now the system has sold one seat twice.

This is a race condition that can lead to double booking.

A suitable design may use database transactions, constraints,
locking, or another concurrency-control mechanism.

The exact solution depends on the architecture and requirements.


KEY IDEA
--------

A feature can work correctly in a simple demonstration and still
fail in production.

System design considers correctness, scale, failures, security,
operations, and cost together.

0.5 SYSTEM DESIGN VS SOFTWARE DEVELOPMENT
================================================================

SOFTWARE DEVELOPMENT
--------------------

Software development involves implementing, testing, debugging,
and maintaining software.

Typical activities:

- Writing code
- Implementing algorithms
- Creating classes and functions
- Writing SQL queries
- Developing APIs
- Writing unit tests
- Fixing bugs
- Refactoring code


SYSTEM DESIGN
-------------

System design focuses on deciding how the overall system should
be structured to meet its requirements.

Typical activities:

- Gathering requirements
- Defining system boundaries
- Selecting architectural patterns
- Designing APIs
- Modeling data
- Selecting databases
- Planning communication between services
- Estimating capacity
- Designing failure handling
- Evaluating trade-offs


EXAMPLE: CHAT APPLICATION
-------------------------

System design decisions:

- Should messages use WebSockets?
- How will messages be stored?
- How will offline messages be delivered?
- How will users authenticate?
- How will the system support many concurrent connections?
- How will message delivery be retried?

Software development tasks:

- Implement the WebSocket handler.
- Write the message persistence code.
- Implement authentication middleware.
- Write database queries.
- Create tests for message delivery.
- Fix bugs in connection management.


COMPARISON
----------

System Design:
    Decides WHAT components are needed and HOW they interact.

Software Development:
    Implements the behavior of those components.

In practice, the activities overlap. Developers often revise
architectural decisions after implementation and testing.


================================================================
0.6 SYSTEM DESIGN VS SYSTEM ARCHITECTURE
================================================================

These terms overlap substantially and are not universally
distinguished in the same way by every engineering organization.


SYSTEM DESIGN
-------------

Often emphasizes the process of turning requirements into a
concrete technical solution.

It can include:

- Requirements analysis
- Component selection
- API contracts
- Data models
- Communication patterns
- Capacity calculations
- Failure handling
- Detailed technical decisions


SYSTEM ARCHITECTURE
-------------------

Often emphasizes the high-level organization of the solution
and its major structural decisions.

It can include:

- Architectural styles
- Service boundaries
- Major components
- Deployment topology
- Data ownership
- Communication between subsystems
- System-wide quality attributes


EXAMPLE
-------

Requirement:
Design an online shopping platform.

Architecture decisions:

- Start with a modular monolith or use microservices.
- Separate the order, payment, and inventory responsibilities.
- Use a relational database for transactional data.
- Use object storage for product images.

Detailed system-design decisions:

- Define the POST /orders API.
- Specify request validation.
- Define order status transitions.
- Design database constraints.
- Decide how payment retries are handled.
- Estimate peak request traffic.


SIMPLE SUMMARY
--------------

Architecture:
    The structure and major technical decisions.

System design:
    The broader process of designing a solution, including
    architecture and the details needed to satisfy requirements.

0.7 LOW-LEVEL DESIGN (LLD) VS HIGH-LEVEL DESIGN (HLD)
================================================================

System design interviews commonly distinguish between LLD and HLD.


A. HIGH-LEVEL DESIGN (HLD)
--------------------------

HLD focuses on the overall architecture and interactions
between major components.

Questions it answers:

1. What services or modules are required?
2. How do they communicate?
3. Which databases are needed?
4. How does the system scale?
5. What happens when a component fails?
6. How is data distributed?
7. How is the system deployed?


EXAMPLE: HLD OF A CHAT APPLICATION

    +-------------+
    | Mobile App  |
    +------+------+
           |
           v
    +-------------+
    | API Gateway |
    +------+------+
           |
           v
    +-------------------+
    | Connection Layer |
    +---------+---------+
              |
              v
    +-------------------+
    | Message Service   |
    +---------+---------+
              |
       +------+------+
       |             |
       v             v
    Message DB     Message Queue
                       |
                       v
                Notification Worker


HLD topics:

- Load balancing
- Database selection
- Caching
- Replication
- Sharding
- Message queues
- Service communication
- Fault tolerance
- Capacity estimation


B. LOW-LEVEL DESIGN (LLD)
-------------------------

LLD focuses on the internal structure and behavior of individual
components.

Questions it answers:

1. Which classes are required?
2. What responsibilities does each class have?
3. Which interfaces are needed?
4. How do objects interact?
5. Which design patterns are appropriate?
6. How should business rules be implemented?
7. How can the design be tested and extended?


EXAMPLE: LLD OF A CHAT APPLICATION

Possible classes:

User
Message
Conversation
MessageService
MessageRepository
NotificationService


Illustrative relationships:

Conversation
    |
    +---- contains ----> Message

MessageService
    |
    +---- uses --------> MessageRepository

MessageService
    |
    +---- uses --------> NotificationService


Simplified pseudocode:

class Message:
    message_id
    sender_id
    conversation_id
    content
    created_at

class MessageService:
    send_message(sender_id, conversation_id, content)
    get_messages(conversation_id)

class MessageRepository:
    save(message)
    find_by_conversation(conversation_id)


HLD VS LLD
----------

HLD:
    How does the entire application work?

LLD:
    How is a particular component designed internally?

HLD example:
    A message service stores messages in a database.

LLD example:
    The MessageService validates input and calls a
    MessageRepository interface to persist the message.


INTERVIEW NOTE
--------------

LLD is not limited to class diagrams, and HLD is not limited
to boxes and arrows.

Good LLD also considers behavior, correctness, testability,
and extensibility.

Good HLD also considers data models, API contracts, and
important operational details.

0.8 FUNCTIONAL REQUIREMENTS
================================================================

DEFINITION
----------

Functional requirements describe WHAT a system must do.

They specify the features, operations, and business behaviors
that the system must provide.


EXAMPLE: E-COMMERCE APPLICATION
-------------------------------

Functional requirements:

FR1: Users can register and log in.

FR2: Users can browse products.

FR3: Users can search for products.

FR4: Users can add products to a cart.

FR5: Users can place orders.

FR6: Users can make payments.

FR7: Users can track their orders.

FR8: Administrators can manage product listings.


EXAMPLE: URL SHORTENER
----------------------

FR1: Create a short URL from a long URL.

FR2: Redirect a short URL to its original destination.

FR3: Reject malformed URLs.

FR4: Support URL expiration if required.

FR5: Allow authorized users to disable their short URLs.

FR6: Collect click statistics if analytics are required.


WHY ARE FUNCTIONAL REQUIREMENTS IMPORTANT?
------------------------------------------

Without clear functional requirements, engineers may build
the wrong product.

For example:

A URL shortener may need only URL creation and redirection.

If analytics, custom aliases, user accounts, and expiration
are not required, implementing all of them immediately may
waste time and resources.


HOW TO IDENTIFY FUNCTIONAL REQUIREMENTS
---------------------------------------

Ask:

1. Who are the users?
2. What actions can each user perform?
3. What information can users create or modify?
4. What results should each operation produce?
5. What errors or invalid operations must be handled?
6. Which features are essential for the first version?


INTERVIEW TIP
-------------

Always distinguish essential requirements from optional features.

For a 45-minute design interview, trying to design every possible
feature can prevent you from exploring the important architecture.


================================================================
0.9 NON-FUNCTIONAL REQUIREMENTS (NFRs)
================================================================

DEFINITION
----------

Non-functional requirements describe the quality attributes,
operational expectations, and constraints of a system.

They help define HOW WELL the system must perform its functions.


COMMON NON-FUNCTIONAL REQUIREMENTS
----------------------------------

1. Performance
2. Scalability
3. Availability
4. Reliability
5. Security
6. Maintainability
7. Durability
8. Observability
9. Accessibility
10. Cost efficiency


EXAMPLE: URL SHORTENER
----------------------

Functional requirement:

The system must redirect a short URL to its original URL.

Non-functional requirements:

- 95% of redirection requests should complete within 100 ms.
- The service should target 99.95% monthly availability.
- URL mappings must survive ordinary application-server failures.
- The service must resist automated abuse.
- Operating costs should remain within the available budget.

These numbers are illustrative targets, not universal standards.


FUNCTIONAL VS NON-FUNCTIONAL
----------------------------

Functional:
    Users can upload a profile picture.

Non-functional:
    The upload should complete within an agreed latency target
    under the expected workload.

Functional:
    Users can search for products.

Non-functional:
    Search must remain responsive during peak traffic.

Functional:
    Users can transfer money.

Non-functional:
    Transfers must preserve financial correctness and prevent
    unauthorized access.


IMPORTANT OBSERVATION
---------------------

Some requirements involve both functional behavior and quality
attributes.

For example:

"Users can recover their accounts securely."

The recovery feature is functional.

The required authentication strength, auditability, and
resistance to account takeover are security requirements.


HOW TO WRITE GOOD NFRs
----------------------

Weak requirement:
    The system should be fast.

Better requirement:
    95% of product-detail requests should complete within
    200 milliseconds at the agreed peak workload.

Weak requirement:
    The system should be highly available.

Better requirement:
    The service should target 99.9% monthly availability,
    with clearly defined measurement and exclusions.

Good requirements are measurable and testable whenever possible.

0.10 CONSTRAINTS
================================================================

DEFINITION
----------

Constraints are conditions or limitations that restrict the
solutions available to the design team.

A system is rarely designed with unlimited time, money,
infrastructure, or freedom to choose technologies.


TYPES OF CONSTRAINTS
--------------------

1. Budget constraints
2. Time constraints
3. Technology constraints
4. Team skill constraints
5. Legal constraints
6. Regulatory constraints
7. Hardware constraints
8. Data residency requirements
9. Compatibility requirements
10. Existing infrastructure


EXAMPLE
-------

You need to design a shopping application.

Constraints:

- The project must launch within three months.
- The initial infrastructure budget is limited.
- The development team is small.
- The organization already uses PostgreSQL.
- Payment processing must use an approved payment provider.


POSSIBLE DESIGN DECISION
------------------------

Instead of immediately creating 20 microservices, start with
a modular monolith.

Use PostgreSQL for transactional data.

Use a managed object-storage service for images.

Introduce additional infrastructure only when justified.


WHY?

Microservices introduce additional operational complexity:

- Network communication
- Service discovery
- Distributed tracing
- Independent deployment management
- Inter-service failure handling
- Distributed data consistency challenges


A simpler architecture may be more appropriate for a small team.


IMPORTANT
---------

A constraint is not necessarily a technical weakness.

It is an input to the design decision.

Good engineers design within constraints rather than pretending
that constraints do not exist.

0.11 ASSUMPTIONS
================================================================

DEFINITION
----------

An assumption is something accepted as true for the purpose of
designing or analyzing a system when the exact information is
not yet known.

Assumptions allow engineers to proceed despite incomplete data.


EXAMPLE
-------

You are asked to design a social-media feed.

The interviewer has not specified the number of users.

You might state:

Assumption 1:
The service has 10 million monthly active users.

Assumption 2:
Each active user opens the feed 5 times per day.

Assumption 3:
Each feed request retrieves approximately 20 posts.

Assumption 4:
The service is read-heavy.

These assumptions help estimate traffic and storage needs.


CALCULATION
-----------

Monthly active users:
    10,000,000

Assumed daily active users:
    2,000,000

Feed requests per active user per day:
    5

Total daily feed requests:

    2,000,000 × 5
    = 10,000,000 requests/day


Average requests per second:

    10,000,000 / 86,400
    ≈ 116 requests/second


If peak traffic is 5 times average:

    Peak traffic
    ≈ 116 × 5
    ≈ 580 requests/second


This is only an illustrative estimate.

The real value depends on actual usage patterns, caching,
traffic distribution, retries, and other factors.


GOOD ASSUMPTIONS
----------------

Good assumptions should be:

- Explicit
- Plausible
- Relevant
- Easy to revise
- Consistent with the problem statement


BAD PRACTICE
------------

Silently assuming billions of users and immediately designing
a globally distributed microservice architecture may introduce
unnecessary complexity.

Start with justified assumptions and scale the design according
to the requirements.


INTERVIEW TIP
-------------

When information is missing:

1. Ask a clarifying question.
2. If clarification is unavailable, state an assumption.
3. Explain how the assumption affects the design.
4. Continue with a reasonable solution.

0.12 TRADE-OFFS
================================================================

DEFINITION
----------

A trade-off occurs when improving one quality or property
makes another property worse, more expensive, or more difficult
to achieve.

System design frequently involves trade-offs because no single
architecture is optimal for every requirement.


TRADE-OFF 1: SQL VS NOSQL
-------------------------

Relational databases commonly provide:

- Structured schemas
- Relationships
- Rich querying
- Transaction support
- Strong consistency options

NoSQL databases may provide:

- Flexible data models
- Workload-specific data access
- Horizontal scaling options
- High throughput for particular access patterns

However, these are general tendencies, not universal rules.

Modern relational and NoSQL databases have overlapping capabilities.

Decision:
Choose according to data relationships, query patterns,
consistency needs, operational requirements, and scale.


TRADE-OFF 2: CACHING
--------------------

Benefits:

- Faster reads for cache hits
- Reduced database load
- Potentially lower response latency

Costs:

- Additional infrastructure
- Cache invalidation complexity
- Memory expense
- Potentially stale data
- More complicated failure behavior


TRADE-OFF 3: MONOLITH VS MICROSERVICES
-------------------------------------

Monolith advantages:

- Simpler deployment
- Easier local development
- Straightforward in-process communication
- Often simpler transactions

Monolith disadvantages:

- Independent scaling of individual modules may be difficult.
- Large codebases can become tightly coupled.
- Deployment may affect the entire application.

Microservices advantages:

- Independent deployment
- Independent scaling
- Clear ownership boundaries when designed well
- Technology flexibility where justified

Microservices disadvantages:

- Network failures
- Distributed tracing requirements
- More operational overhead
- Distributed consistency challenges
- More complicated testing and deployment


TRADE-OFF 4: STRONG CONSISTENCY VS EVENTUAL CONSISTENCY
------------------------------------------------------

Strong consistency:

A successful write is visible to subsequent reads according
to the database's stated consistency guarantees.

Advantages:
- Simpler reasoning for many critical operations.
- Useful for inventory, financial records, and similar data.

Costs:
- May require coordination.
- Some operations can become slower or unavailable under failures,
  depending on the system's design.

Eventual consistency:

Replicas may temporarily disagree but are expected to converge
when updates stop and the system successfully propagates them.

Advantages:
- Can support scalable, geographically distributed workloads.
- Some designs continue accepting updates during certain failures.

Costs:
- Reads may return stale information.
- Applications must handle temporary inconsistencies.
- Conflict resolution may be required.


TRADE-OFF 5: AVAILABILITY VS COST
---------------------------------

Adding replicas and redundant infrastructure can improve
availability.

However, it increases:

- Infrastructure cost
- Operational complexity
- Monitoring requirements
- Deployment complexity


TRADE-OFF 6: LATENCY VS DURABILITY
----------------------------------

A system may acknowledge a write only after durable persistence.

This can increase write latency.

Acknowledging before durable persistence may improve response
time but can risk data loss if a failure occurs before the
data is safely stored.

The appropriate behavior depends on the application's guarantees.


GOLDEN RULE
-----------

Never say that a technology is always the best.

Explain:

1. Why you selected it.
2. What benefit it provides.
3. What drawback it introduces.
4. Why the benefit is worth the drawback for this workload.

0.13 CAPACITY PLANNING
================================================================

DEFINITION
----------

Capacity planning estimates the computing, storage, memory,
network, and database resources required to handle a workload.

It helps engineers avoid under-provisioning and unnecessary
over-provisioning.


WHAT DO WE ESTIMATE?
--------------------

1. Number of users
2. Daily active users
3. Requests per second
4. Peak traffic
5. Read/write ratio
6. Storage growth
7. Network bandwidth
8. Cache memory
9. Database capacity
10. Processing requirements


EXAMPLE: IMAGE-SHARING APPLICATION
----------------------------------

Assume:

Daily active users:
    1,000,000

Average uploads per user per day:
    2

Average uploaded image size:
    2 MB


STEP 1: DAILY IMAGE UPLOADS

    1,000,000 × 2
    = 2,000,000 images/day


STEP 2: DAILY RAW IMAGE STORAGE

    2,000,000 × 2 MB
    = 4,000,000 MB/day


Using decimal units:

    4,000,000 MB
    = 4,000 GB
    = 4 TB/day


STEP 3: ANNUAL RAW IMAGE STORAGE

    4 TB/day × 365
    = 1,460 TB/year
    ≈ 1.46 PB/year


This estimate excludes:

- Image transformations
- Replicas
- Metadata
- Backups
- Deletions
- Compression
- Deduplication
- Storage overhead


STEP 4: ESTIMATE UPLOAD RATE

    2,000,000 uploads/day / 86,400 seconds/day

    ≈ 23.1 uploads/second on average


If peak upload traffic is 4 times average:

    23.1 × 4
    ≈ 92 uploads/second


These are illustrative estimates. Actual traffic may vary
significantly throughout the day.


WHY IS CAPACITY PLANNING IMPORTANT?
-----------------------------------

Without capacity planning:

- Servers may run out of memory.
- Databases may exceed available storage.
- Network links may become bottlenecks.
- Processing queues may grow indefinitely.
- Infrastructure costs may become excessive.


IMPORTANT
---------

Capacity planning estimates the workload first and then
determines the resources needed to support it.

It does not mean purchasing the largest possible servers.


================================================================
0.14 SCALABILITY
================================================================

DEFINITION
----------

Scalability is the ability of a system to handle increased
workload by adding or improving resources while maintaining
acceptable behavior.

Workload can increase through:

- More users
- More requests
- More data
- More simultaneous connections
- More background jobs


TYPES OF SCALING
----------------

A. VERTICAL SCALING
B. HORIZONTAL SCALING


A. VERTICAL SCALING
-------------------

Vertical scaling means increasing the resources of an existing
machine.

Examples:

- More CPU cores
- More RAM
- Faster storage
- A more powerful server


BEFORE:

    Application Server
    4 CPU cores
    8 GB RAM


AFTER:

    Application Server
    16 CPU cores
    64 GB RAM


Advantages:

- Often simpler to implement.
- May require fewer distributed-system mechanisms.
- Can be useful for databases and workloads that scale well
  on a larger machine.

Disadvantages:

- Hardware has practical limits.
- More powerful machines may cost disproportionately more.
- A single machine may remain a failure point.


B. HORIZONTAL SCALING
---------------------

Horizontal scaling means adding more machines or instances.

BEFORE:

    Client
      |
      v
    Server 1


AFTER:

                Client
                  |
                  v
             Load Balancer
              /    |    \
             v     v     v
          Server1 Server2 Server3


Advantages:

- Workload can be distributed.
- Capacity can grow by adding instances.
- Redundancy can improve availability.

Disadvantages:

- Requires coordination between instances.
- Network communication introduces failure possibilities.
- Stateful applications may need shared storage or distributed
  state management.
- Database scaling may remain difficult.


STATELESSNESS
-------------

A stateless application server does not depend on local,
persistent session state from earlier requests to process a
new request.

For example, user session information may be stored in a
shared session store or represented by an appropriately
validated token.

Stateless servers are generally easier to scale horizontally
because requests can be handled by different instances.

However, stateless application servers do not automatically
make the entire system stateless.


SCALABILITY EXAMPLE
-------------------

Suppose one server can handle 1,000 requests per second under
a specified workload.

If traffic rises to 3,000 requests per second, three servers
might appear sufficient.

However, real capacity depends on:

- Request complexity
- CPU utilization
- Memory
- Database throughput
- Network capacity
- Load distribution
- Cache hit rate
- Tail latency
- Headroom requirements

Three servers are not guaranteed to handle exactly three times
the traffic of one server.


INTERVIEW QUESTION
------------------

Q: What is the difference between vertical and horizontal scaling?

Answer:

Vertical scaling increases the resources of an existing machine.
Horizontal scaling adds more machines or instances to distribute
the workload.

Vertical scaling is often simpler, while horizontal scaling can
provide greater aggregate capacity and redundancy at the cost
of additional distributed-system complexity.


================================================================
0.15 RELIABILITY
================================================================

DEFINITION
----------

Reliability is the ability of a system to perform its intended
function correctly over a specified period under specified
conditions.

Reliability includes more than whether a server is running.

The system must also behave correctly.


EXAMPLE
-------

A banking application is reachable, but a transfer operation
sometimes deducts money twice.

The application may be available, but its behavior is unreliable
because it violates financial correctness.


RELIABILITY CONCERNS
--------------------

1. Software defects
2. Hardware failures
3. Network failures
4. Database failures
5. Data corruption
6. Incorrect retries
7. Race conditions
8. Dependency failures
9. Deployment mistakes


HOW CAN RELIABILITY BE IMPROVED?
--------------------------------

1. Automated testing
2. Input validation
3. Database constraints
4. Transactions
5. Redundant components
6. Timeouts
7. Controlled retries
8. Idempotent operations
9. Backups
10. Monitoring and alerting
11. Disaster recovery
12. Graceful degradation


EXAMPLE: PAYMENT RETRIES
------------------------

Suppose a payment request reaches the payment provider.

The provider processes the payment, but the response is lost
because of a network failure.

The application cannot immediately know whether the payment
succeeded.

Blindly sending a new independent payment request can cause
a duplicate charge.

A safer design may use:

- A stable idempotency key
- Persistent payment-operation state
- Provider-supported idempotency
- Reconciliation for uncertain outcomes


RELIABILITY VS AVAILABILITY
---------------------------

Reliability:
    Does the system perform its function correctly over time?

Availability:
    Is the service accessible and ready when required?

A system can be available but unreliable if it returns incorrect
results.

A system can also be reliable during normal operation but have
poor availability because failures cause long outages.


================================================================
0.16 AVAILABILITY
================================================================

DEFINITION
----------

Availability is the proportion of time a service is considered
operational and accessible according to a defined measurement.

A common simplified formula is:

    Availability =
    Uptime / (Uptime + Downtime)


AVAILABILITY EXAMPLE
--------------------

Suppose a service is operational for 999 hours and unavailable
for 1 hour.

Total measured time:

    999 + 1 = 1,000 hours


Availability:

    999 / 1,000
    = 0.999
    = 99.9%


COMMON AVAILABILITY TARGETS
---------------------------

Assuming a 30-day month of 43,200 minutes:

Availability    Approximate monthly downtime

99%             432 minutes
99.9%            43.2 minutes
99.95%           21.6 minutes
99.99%            4.32 minutes
99.999%           0.432 minutes
                 = 25.92 seconds


These figures assume continuous measurement over exactly
30 days and do not define the exclusions in a real SLA.


HOW TO IMPROVE AVAILABILITY
---------------------------

1. Deploy multiple instances.
2. Use health checks.
3. Remove unhealthy instances from service.
4. Replicate critical data appropriately.
5. Eliminate single points of failure.
6. Automate failover where justified.
7. Use multiple availability zones when needed.
8. Monitor dependencies.
9. Perform safe deployments.
10. Test recovery procedures.


EXAMPLE: HIGH-AVAILABILITY API
------------------------------

                  Client
                    |
                    v
               Load Balancer
                 /       \
                v         v
            Server A   Server B
                \         /
                 \       /
                    v
                Database


This design can tolerate an application-server failure if
the load balancer correctly routes traffic to the healthy
instance.

However, the database may still be a single point of failure.

Adding two application servers does not automatically make
the entire system highly available.

Every critical dependency must be considered.


IMPORTANT
---------

High availability is a property of the complete service,
not merely the number of application servers.


================================================================
0.17 PERFORMANCE
================================================================

DEFINITION
----------

Performance describes how efficiently a system responds to
work and processes requests under a specified workload.

Important performance metrics include:

1. Latency
2. Throughput
3. Response time
4. Resource utilization
5. Tail latency
6. Error rate under load


A. LATENCY
----------

Latency is the time taken for an operation or request to
complete, according to the chosen measurement boundaries.

Example:

A product API receives a request at 10:00:00.000.

The response is completed at 10:00:00.150.

Measured response time:

    150 milliseconds


B. THROUGHPUT
--------------

Throughput is the amount of work completed per unit of time.

For a web API, throughput may be measured in requests per second.

Example:

    5,000 completed requests
    ------------------------
          1 second

Throughput = 5,000 requests/second


C. LATENCY VS THROUGHPUT
------------------------

Latency:
    How long does an individual operation take?

Throughput:
    How much work does the system complete per unit of time?


A system can have high throughput but still have unacceptable
latency for some requests.

A system can have low latency for individual requests but
support very little total traffic.


D. PERCENTILES
--------------

Suppose we measure the response times of 10,000 requests.

p50:
    Approximately half the measured requests completed at or
    below this latency.

p95:
    Approximately 95% completed at or below this latency.

p99:
    Approximately 99% completed at or below this latency.


Example:

p50 = 40 ms
p95 = 120 ms
p99 = 500 ms


This means most requests are relatively fast, but the slowest
1% take at least about 500 ms under this distribution.

Percentiles are especially useful because averages can hide
slow requests.


COMMON PERFORMANCE BOTTLENECKS
------------------------------

1. Slow SQL queries
2. Missing database indexes
3. Excessive network calls
4. Large response payloads
5. CPU-intensive processing
6. Memory pressure
7. Lock contention
8. Connection exhaustion
9. Cache misses
10. Slow external dependencies


WAYS TO IMPROVE PERFORMANCE
---------------------------

- Profile before optimizing.
- Optimize database queries.
- Add appropriate indexes.
- Cache frequently accessed data.
- Reduce unnecessary network calls.
- Process suitable work asynchronously.
- Compress large responses when beneficial.
- Use connection pooling.
- Scale bottlenecked components.
- Measure latency percentiles.


IMPORTANT
---------

Do not assume that adding more servers fixes every performance
problem.

If all requests overload one database, adding application
servers may increase database contention instead of improving
performance.


================================================================
0.18 MAINTAINABILITY
================================================================

DEFINITION
----------

Maintainability is the degree to which a system can be
understood, modified, tested, debugged, and improved efficiently.

Software requirements change over time.

A maintainable system allows those changes without creating
unnecessary complexity or excessive risk.


EXAMPLE: POOR MAINTAINABILITY
-----------------------------

Suppose a single 10,000-line class handles:

- Authentication
- Payments
- Database access
- Notifications
- Order processing
- Logging

Changing the payment logic may accidentally break notifications.

Testing individual responsibilities becomes difficult.

This is a sign of poor separation of concerns.


BETTER DESIGN
-------------

AuthenticationService
PaymentService
OrderService
NotificationService
OrderRepository
PaymentRepository


Each component has a more focused responsibility.

This makes the code easier to understand and test.


FACTORS THAT IMPROVE MAINTAINABILITY
------------------------------------

1. Clear module boundaries
2. High cohesion
3. Low unnecessary coupling
4. Consistent naming
5. Automated tests
6. Good documentation
7. Clear API contracts
8. Appropriate abstractions
9. Simple architecture
10. Code review
11. Structured logging
12. Dependency management


COHESION
--------

Cohesion describes how closely related the responsibilities
within a module are.

High cohesion means a module focuses on a coherent purpose.

Example:

A PaymentService that manages payment-related operations
has a clearer responsibility than a class that handles
payments, email delivery, and image resizing.


COUPLING
--------

Coupling describes the degree of dependency between components.

Excessive coupling means a change in one component may require
changes in many other components.

Good modular design aims for appropriate, explicit dependencies
rather than unnecessary interdependence.


IMPORTANT
---------

More classes and more services do not automatically produce
better maintainability.

Unnecessary abstraction and excessive microservices can
increase complexity.

The goal is understandable, testable, appropriately modular
software.


================================================================
0.19 SECURITY
================================================================

DEFINITION
----------

Security is the set of principles, controls, and mechanisms
used to protect a system and its data against unauthorized
access, modification, disclosure, disruption, and misuse.


CORE SECURITY GOALS
-------------------

A. CONFIDENTIALITY

Only authorized parties should be able to access protected data.

Example:
A user must not be able to read another user's private messages.


B. INTEGRITY

Data should not be modified improperly.

Example:
A customer must not be able to change the price of an order
by modifying an HTTP request.


C. AVAILABILITY

Authorized users should be able to access the service when
required.

Example:
Rate limiting and DDoS mitigation may help protect service
availability against abusive traffic.


AUTHENTICATION
--------------

Authentication answers:

    WHO ARE YOU?

Examples:

- Password-based login
- Multi-factor authentication
- Passkeys
- Identity-provider login


AUTHORIZATION
-------------

Authorization answers:

    WHAT ARE YOU ALLOWED TO DO?

Example:

A user successfully logs in.

However, that user should not automatically gain permission
to access another customer's order.


COMMON SECURITY MEASURES
------------------------

1. HTTPS/TLS
2. Secure password hashing
3. Input validation
4. Authorization checks
5. Least-privilege permissions
6. Secrets management
7. Encryption where appropriate
8. Rate limiting
9. Security logging
10. Dependency updates
11. Secure session management
12. Protection against injection attacks
13. Backup protection
14. Regular security testing


EXAMPLE: INSECURE API
---------------------

GET /users/12345/orders


Suppose a logged-in user changes the identifier to:

GET /users/67890/orders


If the server returns another user's orders without checking
authorization, the application has an access-control vulnerability.


SECURE APPROACH
---------------

The server must verify that the authenticated principal is
authorized to access the requested user's orders.

Hiding the identifier in the user interface is not sufficient.


SECURITY BY DESIGN
------------------

Security should be considered during architecture and
implementation rather than added only after deployment.

The design should consider:

- Threats
- Trust boundaries
- Authentication
- Authorization
- Data protection
- Abuse prevention
- Auditability
- Incident response

0.20 OBSERVABILITY
================================================================

DEFINITION
----------

Observability is the ability to understand a system's internal
state by examining the outputs it produces.

These outputs commonly include:

1. Logs
2. Metrics
3. Distributed traces


A. LOGS
-------

Logs record events that occur in the system.

Example:

    timestamp: 2026-10-10T10:00:00Z
    level: ERROR
    service: payment-service
    message: Payment provider request timed out
    request_id: req-12345


Logs help engineers investigate specific events and errors.


B. METRICS
----------

Metrics are numerical measurements collected over time.

Examples:

- Requests per second
- Error rate
- CPU utilization
- Memory utilization
- Database connection count
- Queue depth
- p95 response latency


Example:

    API requests per second = 5,000

    API error rate = 0.5%

    p95 latency = 120 ms


Metrics help engineers identify trends, bottlenecks, and
potential incidents.


C. DISTRIBUTED TRACING
----------------------

Distributed tracing follows a request as it moves through
multiple services.

Example:

    Client
      |
      v
    API Gateway
      |
      v
    Order Service
      |
      v
    Payment Service
      |
      v
    Payment Provider


A trace may reveal that:

- API Gateway: 5 ms
- Order Service: 15 ms
- Payment Service: 900 ms
- Payment Provider: 850 ms


The trace helps identify the slow dependency.


WHY IS OBSERVABILITY IMPORTANT?
-------------------------------

Imagine users report that payments are failing.

Without observability, engineers may not know:

- Which service is failing.
- Whether the database is healthy.
- Whether the payment provider is slow.
- Whether failures affect all users.
- Whether a recent deployment caused the issue.
- Whether the system is running out of capacity.


OBSERVABILITY VS MONITORING
---------------------------

Monitoring typically tracks known conditions and alerts when
measurements cross defined thresholds.

Observability also supports investigating unfamiliar problems
by examining system telemetry and relationships between events.

The two concepts complement each other.


OBSERVABILITY EXAMPLE
---------------------

A useful payment-system dashboard may show:

- Payment success rate
- Payment failure rate
- Provider timeout count
- Request latency percentiles
- Queue depth
- Database connection utilization
- Retry volume


Alerts might notify the team when the payment success rate
falls below an agreed threshold.

The team can then inspect logs and traces to investigate
the underlying cause.

ASSUMPTIONS
-----------

-----------

AVAILABILITY
------------
The proportion of measured time the service is operational
and accessible according to a defined criterion.


PERFORMANCE
-----------
How efficiently the system processes requests and completes work.


MAINTAINABILITY
---------------
How easily the system can be understood, tested, modified,
and improved.
